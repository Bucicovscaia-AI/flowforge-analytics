### Dataset choice

A **fabricated retail sales orders dataset** (about 500 rows), generated by a
seeded Python script so it can be reproduced. Columns: `order_id`,
`order_date`, `region`, `channel`, `product_category`, `quantity`,
`unit_price`, `customer_type`. A few deliberate problems (blank cells,
duplicate orders, a negative quantity, an unparseable date) will be injected so
the data-quality checks have something real to find.

Planned KPIs: total revenue, number of orders, average order value, revenue by
month (trend chart), revenue by region and by category, and a data-quality
score (share of rows that passed validation).

## 4. Key technical decisions (Stage 1)

* **Monorepo with `frontend/` and `backend/`.** One Git repository keeps the
  whole project in one place for the portfolio, while the two folders keep a
  clear boundary between the user interface and the data processing.
* **Vite dev proxy.** The React app calls `/api/...` and Vite forwards it to
  FastAPI on port 8000. The browser then sees a single origin, which avoids
  cross-origin (CORS) problems in development. CORS is still configured in
  FastAPI for other setups.
* **Service layer (`frontend/src/services/api.js`).** Components never call
  `fetch` directly. All network code and error handling sit in one file, so
  if an endpoint changes only one place needs editing, and every component
  gets the same readable error messages.
* **Settings from environment variables (`backend/app/config.py`).** Limits
  and future secrets come from a `.env` file that Git ignores. `.env.example`
  documents the variables without real values.
* **Pinned dependency versions.** `requirements.txt` pins exact versions so the
  project installs the same way on the marker's machine.
* **Tailwind CSS v4 through its Vite plugin.** No separate config file is
  needed; utility classes keep styling consistent without writing custom CSS.
* Frontend unit tests (Vitest) are deferred to Stage 2, when there are
  components worth testing. Backend tests use pytest from the start.

## 6. Access for the lecturer (added 27 Oct)

Requirement: the lecturer must be able to test the application from his own
device.

**Recommended approach: one hosted service.** FastAPI serves the built React
files as well as the `/api` endpoints, and the whole app is deployed as a
single free web service on Render (render.com), connected to the GitHub
repository so each push redeploys automatically.

| Option | For | Against |
| --- | --- | --- |
| **One Render web service (recommended)** | One link to share; no CORS setup; one deployment to maintain | Free services sleep when idle, so the first visit can take about a minute to wake |
| Frontend on Vercel or Netlify + backend on Render | Fast static frontend | Two deployments, two URLs, CORS and environment settings to keep in sync |
| Local run only | No hosting account needed | The lecturer must install Python and Node.js |

Plan: add the static-file serving and deployment config in Stage 5, once the
frontend calls the real API, and deploy it then so there is time to fix
hosting problems before 30 October. Cristina will need a free Render account
signed in with GitHub. The README's local-run instructions stay as the
fallback.
